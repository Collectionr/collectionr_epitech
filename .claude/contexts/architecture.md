# Architecture backend — Décisions (ADRs)

Règle de dépendance absolue (détail dans `docs/backend/clean-architecture.md`) :

```
interface → application → domain
                ↑
         infrastructure (implémente les ports de application/)
```

## ADR-001 — Fastify plutôt qu'Express

Adaptateur `@nestjs/platform-fastify`.
**Raison** : SLA API < 200 ms P95 (CDC) ; Fastify est sensiblement plus rapide et son logger natif est pino — cohérent avec le logging structuré.
**Conséquence** : accès natif `@Res()` interdit sauf nécessité documentée (cf. conventions) ; les plugins sont des packages `@fastify/*`.

## ADR-002 — Socle transverse centralisé dans `configureApp()`

Toute la configuration d'app (préfixe, versioning, pipes, CORS, Helmet, Swagger) vit dans `src/shared/bootstrap/ConfigureApp.ts`, appelée par `main.ts` **et** par chaque test e2e.
**Raison** : les e2e exercent exactement la configuration de production ; aucun endpoint ne peut « oublier » une garantie du socle.

## ADR-003 — `/health` hors préfixe `/api/v1`

`setGlobalPrefix('api', { exclude: ['health'] })` + `VERSION_NEUTRAL` sur le controller.
**Raison** : les Liveness/Readiness Probes K3s (équipe Cloud & Cyber) ciblent une URL stable, indépendante du versioning API.

## ADR-004 — Healthcheck via ports + clients légers (pré-Prisma)

`/health` vérifie la connexion effective : `SELECT 1` (pool `pg`) et `PING` (ioredis), timeout 2 s, latence mesurée. Les vérifications passent par le port `IHealthIndicator` (token `HEALTH_INDICATORS`).
**Raison** : l'outillage Prisma est porté par COLLR-412 — hors périmètre du socle (COLLR-411). Grâce au port, brancher Prisma = remplacer `PostgresHealthIndicator`, sans toucher use case, controller ni tests.
**Statut** : **remplacé par ADR-010 (COLLR-437)**. `PostgresHealthIndicator` (pool `pg`) n'existe plus.

## ADR-010 — Healthcheck via Prisma (driver adapter `@prisma/adapter-pg`)

`PostgresHealthIndicator` est remplacé par `PrismaHealthIndicator`, même port `IHealthIndicator`, même contrat `DependencyHealth`, même timeout 2 s (`runWithTimeout`). La vérification passe par `prismaClient.$queryRaw\`SELECT 1\`` au lieu de `pool.query`. `PostgresModule` (pool `pg` brut) est remplacé par `PrismaModule` (token `PRISMA_CLIENT`), qui instancie `PrismaClient` avec l'adapter `PrismaPg({ connectionString: DATABASE_URL })` — Prisma 7 ne se connecte plus via une `url` dans `schema.prisma` (cf. `.claude/errors/prisma7_url_in_schema.md`).
**Raison** : ADR-004 était explicitement transitoire ; le port `IHealthIndicator` a permis ce remplacement sans toucher `GetHealthStatusUseCase`, `HealthController` ni leurs tests — seul `HealthModule.ts` change de câblage.
**Détails d'implémentation** :
- Client généré dans `src/generated/prisma/` (pas à la racine de `backend/`, pour rester sous le `rootDir` TypeScript de `nest build` — sinon `dist/main.js` se retrouve sous `dist/src/main.js` et casse `start:prod`). Dossier gitignoré, régénéré via `postinstall`/`npm run prisma:generate`.
- `prisma.config.ts` (config migrate, cf. piège Prisma 7) est exclu de `tsconfig.build.json` pour la même raison de `rootDir`.
- Jest a besoin d'un `moduleNameMapper` (`^(\\.{1,2}/.*)\\.js$` → `$1`) : le client généré importe ses propres fichiers internes en NodeNext (extension `.js` explicite sur des `.ts`), que le resolver Jest par défaut ne résout pas.
- Aucun modèle métier dans `schema.prisma` à ce stade (périmètre COLLR-412/437) ; `prisma migrate dev`/`deploy` validés contre une instance PostgreSQL 16 réelle (créent `_prisma_migrations`, aucune migration à générer tant qu'il n'y a aucun modèle).
**Statut** : actif.

## ADR-005 — Config par connection strings, validée au démarrage

`DATABASE_URL` / `REDIS_URL` au format URL (pas de variables éclatées `DB_HOST`/`DB_USER`/…), classe `EnvironmentVariables` validée par class-validator via `ConfigModule.forRoot({ validate })`. L'app **refuse de démarrer** si une variable requise est absente/invalide, en listant les erreurs.
**Raison** : format attendu par Prisma et fourni par les PostgreSQL managés ; fail-fast au boot plutôt que crash à la première requête en prod. Aucun secret n'a de valeur par défaut (`JWT_SECRET` ≥ 32 caractères obligatoire).

## ADR-006 — Format d'erreur API unique

`AllExceptionsFilter` (global, via `APP_FILTER`) renvoie toujours `{ statusCode, error, message, timestamp, path }`. Toute erreur 5xx — non-HTTP **ou** `HttpException` de statut ≥ 500 (ex. `ServiceUnavailableException`) — renvoie un corps générique (`error` = libellé HTTP standard, `message` = « An internal error occurred »). Le vrai message et la stack ne sont que dans les logs serveur. Les 4xx conservent leur message (utile au client).
**Raison** : contrat stable pour le frontend quel que soit le domaine ; aucune fuite de détail interne (retour de review PR COLLR-411 : une `HttpException` 5xx renvoyait auparavant son message tel quel) ; les erreurs du ValidationPipe (tableau `message[]`) sont préservées.

## ADR-007 — Logs JSON via nestjs-pino

JSON une ligne/événement hors développement, `pino-pretty` en dev, niveau par `LOG_LEVEL`, redaction de `authorization`/`cookie`/`set-cookie`. Hors développement, même forme de ligne que le microservice TCG : `level` en texte (`"info"`, pas `30`), `time` en ISO 8601, champ `service` (S05), pour filtrer les deux services avec les mêmes requêtes Loki.
**Raison** : base exploitable par Grafana/Loki (observabilité portée par Cloud & Cyber) ; pino est le logger natif de Fastify (quasi zéro overhead).

## ADR-008 — Rate limiting à deux niveaux

Throttler global (`THROTTLE_TTL`/`THROTTLE_LIMIT`, guard `APP_GUARD`) comme filet de sécurité ; le rate limiting renforcé de `/login` et `/register` sera porté par l'Epic Authentification (stockage Redis, pas en mémoire).
**Raison** : protection de base immédiate sur toute l'API sans attendre l'auth.

## ADR-009 — CSP Helmet assouplie uniquement si Swagger UI exposé

`@fastify/helmet` global ; quand `SWAGGER_ENABLED=true`, la CSP autorise les scripts/styles inline requis par Swagger UI. En production (Swagger désactivé), CSP stricte par défaut.
**Raison** : ne pas dégrader la posture sécurité prod pour un outil de dev.

## ADR-011 — Journalisation d'audit par décorateur `@Audit` + interceptor global (COLLR-413)

Module `src/modules/audit/`. Table `audit_logs` (colonnes du schéma `docs/database/schema-sql.md` : `userId`, `action`, `targetType`, `targetId`, `metadata`, `timestamp`, `expiresAt`). Un handler annoté `@Audit({ action, targetType?, targetIdParam?, bodyFields? })` est tracé par `AuditInterceptor` (enregistré en `APP_INTERCEPTOR` par `AuditModule`, sans effet sur les routes non annotées). Tout autre code peut aussi injecter `RecordAuditEntryUseCase`.
**Décisions** :
- **`action` en string libre** au format `domaine.verbe` (validé par `AuditEntry.isValidAction`, et par `@Audit` au démarrage). Un échec est enregistré sous `<action>.failed` avec `statusCode` en metadata — pas de colonne `outcome` (absente du schéma).
- **Écriture synchrone** (le `await` a lieu avant l'envoi de la réponse) ; si elle échoue, l'erreur est **loguée en ERROR et n'interrompt pas** la requête métier (fail-open, choix Alpha : une table d'audit en panne ne doit pas bloquer les connexions). Passer en fail-closed = ne plus attraper l'erreur dans `AuditInterceptor.write`.
- **`metadata` en liste blanche** : seuls les champs de `bodyFields` sont copiés (+ `requestId` pour la corrélation des logs) ; jamais le body brut. `@Audit` refuse au démarrage un champ au nom sensible (`password`, `token`, `secret`… — `domain/rules/SensitiveFields.ts`). Règle S05 §6.
- **`expiresAt`** = `timestamp` + `AUDIT_LOG_RETENTION_DAYS` (défaut 90 j, S04) calculé à l'écriture par `AuditEntry.record`.
- **`userId` nullable, sans FK** : la table `users` n'existe pas encore, et les connexions ratées sont anonymes. L'interceptor lit `request.user.id` (uuid) quand il existe. COLLR-442 ajoutera la FK (`ON DELETE SET NULL`, pour qu'une suppression de compte RGPD ne détruise pas la trace).
- **Journal en ajout seul** : le port `IAuditLogRepository` n'expose que `record`.
- **Rejets de guard (401/403/429) capturés malgré tout** : un interceptor NestJS ne s'exécute jamais quand un guard rejette une requête (guards → interceptors dans le pipeline). `AuditContextGuard` (global, enregistré **avant** `ThrottlerGuard` dans `AppModule` — l'ordre des `APP_GUARD` compte) se contente d'observer et de poser les options `@Audit` sur la requête si la route en porte. `AllExceptionsFilter` — seul point du pipeline exécuté après *n'importe quel* guard — consomme ce marqueur et enregistre `<action>.failed` si présent. `AuditInterceptor` consomme (et efface) le même marqueur dès qu'il s'exécute, donc jamais de double-écriture entre les deux chemins. `writeAuditEntry` (`modules/audit/interface/WriteAuditEntry.ts`) factorise l'écriture + le fail-open entre les deux. **Conséquence assumée** : `shared/interface/filters/AllExceptionsFilter.ts` dépend désormais de `modules/audit/` — inversion volontaire de la couche `shared`, acceptée pour garder un seul filtre source de vérité du format d'erreur (ADR-006) plutôt que d'empiler plusieurs `APP_FILTER` globaux (comportement non garanti par NestJS quand plusieurs filtres globaux matchent la même exception).
- **`metadata` : défense en profondeur par forme de valeur.** En plus de la liste blanche `bodyFields` et du refus au démarrage des noms de champs sensibles (`SensitiveFields.ts`, élargi : `apiKey`, `pin`, `cvv`, `ssn`, `iban`), `ReadAuditContext.ts` redige (`"[redacted]"`) toute valeur qui *ressemble* à un JWT ou à un hash bcrypt/argon2, **quel que soit le nom du champ whitelisté**. Ça ne couvre pas tout (un champ nommé innocemment mais contenant un secret arbitraire sans forme reconnaissable resterait visible) — mais ça retire la dépendance totale à la vigilance du développeur pour les deux cas les plus probables (un token ou un hash qui traîne dans un champ autorisé par erreur).
**Limite connue restante** : la **purge** des entrées expirées n'est pas implémentée (déclencheur à trancher avec Cloud/DevOps, cf. `project_state.md`).

## ADR-012 — Table `data_retention_policies` sans module applicatif (COLLR-664)

Modèle Prisma `DataRetentionPolicy` → table `data_retention_policies` (colonnes de `docs/database/schema-sql.md` : `id`, `entityType`, `retentionDays`, `description`, `updatedAt`). Données de référence des durées S04 §5 : écrites par le seeder (COLLR-543), lues par le cronjob de suppression (COLLR-544), tous deux hors `backend/`.
**Décisions** :
- **Pas de module Clean Architecture** (ni port, ni repository, ni use case) : aucun code backend ne lit la table. Même principe que COLLR-412/437. Un module sera créé quand un use case en aura besoin.
- **Mêmes conventions que `audit_logs`** : nom de table snake_case pluriel (`@@map`), `id` en `@db.Uuid`, dates en `@db.Timestamptz(6)`.
- **`entityType` unique** : une seule politique par type de donnée. Sinon le cronjob ne saurait pas quelle durée appliquer, et le seeder peut faire un `upsert` idempotent sur `entityType`. Les valeurs sont en snake_case singulier (`account`, `application_log`, `audit_log`…) ; la liste définitive revient au seeder.
- **`retentionDays` est compté depuis l'événement de référence de chaque type** (clôture du compte pour `account`, création pour les logs), pas depuis `updatedAt`.
**Limites connues** :
- Pas de contrainte `CHECK (retentionDays >= 0)` : Prisma ne sait pas la déclarer dans le schéma. À ajouter en SQL dans une migration si un besoin de validation en base apparaît.
- **Deux sources pour la rétention d'audit** : `AUDIT_LOG_RETENTION_DAYS` (variable d'env, calcule `audit_logs.expiresAt` à l'écriture, ADR-011) et la ligne `audit_log` de cette table. Elles doivent rester égales (90 j) jusqu'à ce que COLLR-544 décide laquelle fait foi.

## ADR-013 — Tables RBAC `roles` / `permissions` / `role_permissions` sans module applicatif (COLLR-665)

Modèles Prisma `Role`, `Permission`, `RolePermission` (colonnes de `docs/database/schema-sql.md` : `id` + `name` pour les deux premiers, `roleId` + `permissionId` pour la jointure). Migration `prisma/migrations/20260924132529_add_roles_permissions`. Le RBAC repose sur un modèle relationnel (et non un enum Prisma) pour que `users.roleId` soit une vraie FK dès la création de la table `users` (COLLR-447) — pas de migration enum → FK à prévoir plus tard.
**Décisions** :
- **Mêmes conventions que `audit_logs`** (ADR-011) : tables snake_case pluriel (`@@map`), `id` en `@db.Uuid` + `@default(uuid())`.
- **`Role.name` et `Permission.name` uniques** : un rôle / une permission est identifié par son nom dans le code (jamais par son UUID, qui diffère d'un environnement à l'autre), et le seed fait un `upsert` idempotent dessus.
- **Deux rôles seulement : `USER` et `ADMIN`** (décision du 2026-10-12). `MODERATOR` (« optionnel » dans S03 §5.2 et le CDC) est retiré du seed : il n'a aucun périmètre défini, et le back-office d'administration (CDC §3.5, UC-09/10) n'arrive qu'au jalon V1. Sa réintroduction et ses droits sont à cadrer dans COLLR-679 (matrice des droits). L'ajouter plus tard = une valeur dans `ROLE_NAMES` + une ligne en base, sans migration de structure. Pour l'Alpha, `USER` et `ADMIN` ne diffèrent que par l'obtention du rôle : inscription → `USER`, `ADMIN` attribué hors API.
- **Casse** : rôles en MAJUSCULES (`USER`, `ADMIN`, S03 §5.2 + Jira) ; `documentation-metier.md` les écrivait en minuscules → doc alignée. Permissions au format `ressource:action` en minuscules (`collection:write`, `card:delete` — `documentation-metier.md`).
- **Liste des rôles = constante `ROLE_NAMES`** (+ type `RoleName`) dans `src/shared/config/AppConstants.ts`, partagée entre le seed et les futurs modules Auth (COLLR-447) et RBAC (COLLR-449). Aucune chaîne de rôle en dur ailleurs.
- **`role_permissions`** : clé primaire composite `(roleId, permissionId)` (pas d'`id` technique, empêche les doublons), FK `ON DELETE CASCADE` des deux côtés — supprimer un rôle ou une permission supprime ses associations, jamais l'inverse (vérifié en SQL sur PG16).
- **Pas de permission seedée** : aucune liste n'est définie dans `docs/`. À définir avec l'équipe avant COLLR-449 (TODO dans `project_state.md`).
- **Pas de module Clean Architecture** (ni port, ni repository, ni guard, ni `@Roles`) : aucun code ne lit ces tables. Même principe qu'ADR-012 (COLLR-664). Le contrôle d'accès arrive avec COLLR-449.
- **Relation `User → Role` réalisée (COLLR-415, migration `20261021120000_users_role_fk`)** : `users.roleId` est une FK `NOT NULL` vers `roles` (`ON DELETE RESTRICT` : un rôle qui a des comptes ne se supprime pas). L'enum `UserRole` est supprimé. À l'inscription, le compte est relié au rôle `USER` **par son nom** (`REGISTRATION_ROLE`, typé `RoleName`), jamais par UUID. Le domaine ne connaît pas le rôle avant COLLR-449.
**Décision (2026-10-21) — rôles insérés par la migration.** La migration `20261021120000_users_role_fk` insère `USER` et `ADMIN` dans `roles` (`ON CONFLICT ("name") DO NOTHING`) avant de poser la FK : chaque environnement, production comprise, a ses rôles de référence sans dépendre du seed. Le seed reste idempotent (upsert par nom) et ne contient aucune donnée de démo en prod. Les deux listes (migration et `ROLE_NAMES`) doivent rester synchronisées ; un test d'intégration vérifie que le compte créé porte le rôle `USER`.


## ADR-014 — Module Auth : algorithme de hachage, politique de mot de passe, frontières domaine/infra (COLLR-414)

Module `src/modules/auth/` (`domain/` + `application/`, sans infrastructure ni endpoint : COLLR-415 les branche).
**Décisions** :
- **bcrypt retenu** comme algorithme de hachage (WBS 3.3, COLLR-510, S04 §2.2). Le CDC et S03 disent « bcrypt ou Argon2 » : le choix est désormais tranché ici. Passer à Argon2 ne change que l'adaptateur de `IPasswordHasher`.
- **Rien de propre à l'algorithme dans `domain/` ni `application/`.** Ce qui en dépend est fourni par le port `IPasswordHasher` : `maxPasswordBytes` (bcrypt ne lit que 72 octets ; `Password.create` reçoit la limite en paramètre, comme `minLength`) et `getDummyHash()` (hash factice au même coût que les vrais, pour que le login d'un compte inconnu prenne autant de temps qu'un compte connu). Une constante écrite dans un use case dérive en silence quand le coût ou l'algorithme change (mesuré : coût 10 = ~64 ms contre coût 12 = ~254 ms).
- **Politique de mot de passe** : 8 caractères minimum (`PASSWORD_MIN_LENGTH`, 8 à 64), au moins une lettre et un chiffre Unicode (`\p{L}`, `\p{Nd}`), pas de caractère nul. **Décision produit à valider par le PO** : le CDC ne fixe aucune règle. Une valeur de politique absente ou invalide fait échouer la création (erreur 5xx), elle ne désactive jamais la règle.
- **Les use cases ne renvoient jamais `passwordHash`** : ils renvoient `UserProfile` (`application/dtos/UserProfile.ts`). Un contrôleur ne peut pas divulguer ce qu'il ne reçoit pas.
- **Comptes désactivés (`isActive`)** : refusés par `Login`, `UpdateProfile` et `ChangePassword` avec la même erreur qu'un compte inconnu. Le refus des tokens (refresh, access) est une obligation du contrat de `IAuthTokenService`, à implémenter en COLLR-415.
- **Messages d'erreur fixes** : `EmailAlreadyUsedError`, `UserNotFoundError` ne reprennent ni l'email ni l'identifiant reçus. `DomainValidationError` est la seule erreur de domaine convertible en 4xx.
- **Email canonique** (NFKC, minuscules, domaine en punycode, sans guillemets ni caractères invisibles) : une boîte mail, un seul compte.
**Points ouverts / suites** :
- **CGU et consentement (retour de relecture, traité en COLLR-414)** : `consentGivenAt` est remplacé par `termsAcceptedAt` + `termsVersion` sur `User`. L'inscription enregistre l'acceptation du contrat (S04 §4 : exécution du contrat), pas un consentement RGPD optionnel ; la table `CONSENT` de `schema-sql.md` reste réservée à ces derniers (Beta). Le client envoie la version qu'il a affichée (`acceptedTermsVersion`), le serveur la compare à `TERMS_VERSION` et refuse une version périmée (`TermsVersionMismatchError`) : c'est la preuve de ce qui a été accepté. `TERMS_VERSION` doit être modifiée à chaque changement des CGU publiées. Reste pour COLLR-415 : colonnes `termsAcceptedAt` / `termsVersion` dans la migration, DTO d'inscription (`acceptedTermsVersion` à la place de `hasAcceptedTerms`).
**Pseudo unique, insensible à la casse (retour de relecture, traité en COLLR-414)** : `User.usernameKey` (NFKC, minuscules, espaces repliés) définit l'égalité de deux pseudos ; `IUserRepository.findByUsername`, vérification dans `RegisterUser` et `UpdateProfile` (changer seulement la casse de son propre pseudo reste permis), `UsernameAlreadyUsedError`, contrat de `save()` (rejet sous concurrence). Reste pour COLLR-415 : la colonne de clé canonique et son index unique, et la traduction de la violation de contrainte en `UsernameAlreadyUsedError`. Les lettres d'autres alphabets qui ressemblent à des lettres latines ne sont pas repliées (il faudrait une table de confusables).
**Désactivation (retour de relecture, traité en COLLR-414)** : `DeactivateUserUseCase` désactive d'abord (plus aucune nouvelle session), puis révoque toutes les sessions du compte ; il est idempotent, donc rejouable si la révocation échoue. Qui peut l'appeler (admin) relève d'un garde de rôle côté interface.

## ADR-015 — Catalogue `licences_tcg` / `sets` / `cards` / `variants` : contrat d'interface possédé par le backend (COLLR-684)

Modèles Prisma `LicenceTCG`, `CardSet`, `Card`, `Variant` → tables `licences_tcg`, `sets`, `cards`, `variants` (migration `prisma/migrations/20261025120000_add_card_catalogue`). Le backend possède le schéma et le migre ; le microservice TCG (Python, psycopg) ne crée ni ne modifie aucune table et n'y écrit que par UPSERT, sur les clés uniques du contrat. Même règle que `docs/microservices/architecture-microservices.md` (PostgreSQL = source de vérité, UPSERT idempotents). Le module applicatif `catalogue` (domaine + repository de lecture) vient avec l'ADR-016 ; ses use cases et ses endpoints (recherche, autocomplétion) sont ceux de COLLR-418 et COLLR-407.
**Décisions** :
- **Clés d'UPSERT** : `licences_tcg.slug`, `sets.tcgdexId`, `cards.tcgdexId`, toutes `UNIQUE NOT NULL`, et `variants.(cardId, tcgdexVariantId)` (clé composite, voir plus bas). `tcgdexId` est l'identifiant TCGdex tel quel (`base1`, `swsh3`, `sv03.5`, `swsh3-20`), identique dans toutes les langues. L'`id` UUID reste la clé technique que les futures FK (collection, wishlist) référencent.
- **`id` généré par la base** (`DEFAULT gen_random_uuid()`, `@default(dbgenerated(...))`) et non par `@default(uuid())` comme les tables précédentes : l'UUID de Prisma est produit côté client, donc un `INSERT … ON CONFLICT` en SQL brut devrait en fournir un. Ces tables sont écrites par un autre service, le défaut doit être en base.
- **Une ligne par set et par carte ; noms en deux langues, vocabulaires fixes en anglais seulement.** `nameEn` est obligatoire et `nameFr` optionnel (TCGdex ne couvre le français qu'à ~95 %) ; même principe pour l'évolution précédente (`evolveFromEn`/`evolveFromFr`), la série, l'abréviation et les images. En revanche `category`, `rarity`, `types` et `stage` n'ont **qu'une colonne, en anglais** : ce sont des codes que le front traduit avec un fichier de langue (pratique courante : les filtres et les tris ne dépendent pas de la langue, et une langue de plus ne demande aucune migration). Le front affiche le texte anglais pour une valeur qu'il ne connaît pas encore, car TCGdex ajoute des raretés avec chaque set et ne les normalise pas toutes ; les colonnes restent donc du texte, pas un `enum` PostgreSQL. Les valeurs observées et leur libellé français sont dans `docs/database/schema-sql.md`.
- **`number` = `localId` TCGdex, en texte** : zéros initiaux (`006`) et préfixes (`TG01`) à conserver.
- **`types` en `TEXT[]`** (défaut vide) : une carte peut avoir plusieurs types. `hp` nullable. Les cartes Dresseur et Énergie n'ont en général ni l'un ni l'autre, mais TCGdex en renseigne quelques-unes (Fossiles, Poupée Mélo, Énergie Psy de `sv03.5`) : ne pas les supposer toujours vides.
- **Variantes : `variantId` de TCGdex n'est pas une clé à lui seul.** Mesuré sur les 3 sets de référence : 1163 impressions, mais seulement 21 `variantId` distincts partagés entre cartes (les 16 premières cartes de `base1` portent les mêmes quatre, comme les Énergies). Il identifie un *type* d'impression, pas une impression de cette carte : la clé est donc `(cardId, tcgdexVariantId)`, unique dans chaque carte. `variants` porte `type`, `subtype`, `size`, `stamps`, `foil` et les identifiants produit Cardmarket / TCGPlayer / CardTrader (pour rattacher les prix plus tard). Les codes sont stockés **en anglais seulement** (kebab-case) : les libellés français de TCGdex sont en partie non traduits (`thank-you`, `pikachu`). Les drapeaux `variants` de TCGdex (normal, reverse, holo, 1re édition…) ne sont **pas** recopiés sur `cards` : ils ne concordent pas toujours avec le détail (121 cartes sur 510, surtout `base1`) et se déduisent de `variants`.
- **Informations de jeu conservées sur `cards`** : `illustrator`, `dexIds` (numéros du Pokédex national, `INTEGER[]`), `evolveFromEn` / `evolveFromFr` (l'évolution précédente), `stage`, `tcgdexUpdatedAt` (le `updated` de TCGdex). Sur `sets` : série (id + noms en/fr), `abbreviationOfficial` / `abbreviationFr`, `tcgOnlineCode`, décomptes par type d'impression.
- **Écartés à la relecture** (informations de joueur ou filtres sans usage pour un collectionneur, le CDC excluant le compétitif) : `regulationMark` (la lettre imprimée en bas des cartes récentes, qui décide de leur sortie du format Standard), la légalité en tournoi (`legal`, cartes et sets), `suffix` (V, ex : déjà dans le nom), `trainerType` (Objet, Supporter, Stade, Outil) et `energyType` (énergie de base ou spéciale, 12 cartes sur 510).
- **`licences_tcg.logoUrl`** : URL nullable, vide dans le seed (TCGdex ne fournit aucun logo de licence) ; la source reste à choisir, rien n'est stocké localement.
- **Images : URL de base du CDN TCGdex uniquement**, sans extension, par langue (`imageUrlEn`, `imageUrlFr`) ; logos de set par langue, symbole commun. Aucun fichier stocké (CDC, volet propriété intellectuelle : « aucun stockage local d'images »).
- **Clés étrangères en `ON DELETE RESTRICT`** (`sets.licenceTCGId`, `cards.setId`, `variants.cardId`) : un catalogue référencé par des collections ne se vide pas par cascade.
- **Dates et effectifs** : `releaseDate` (type `DATE`) remplace `year` du schéma initial (TCGdex fournit la date complète ; l'année s'en déduit pour le filtre « année » du CDC). `officialCardCount` / `totalCardCount` remplacent `totalCards` (189 / 201 pour `swsh3` : la complétude d'une collection se calcule sur le total).
- **`updatedAt` n'est maintenu que par Prisma** : `@updatedAt` s'exécute côté client. Un UPSERT en SQL brut doit écrire `updatedAt = now()` lui-même (le défaut ne joue qu'à l'insertion). Aucun code du backend ne lit `updatedAt` du catalogue : la fraîcheur d'une carte est `tcgdexUpdatedAt`, d'où l'absence de trigger (logique invisible pour Prisma, hors de la convention des autres tables). À reconsidérer si un consommateur apparaît (ETag ou invalidation de cache pour COLLR-418, affichage admin).
- **Nom du modèle `CardSet`** : un modèle `Set` masquerait le `Set` global dans le client généré. La table reste `sets`.
- **Hors contrat, volontairement** : prix (`CardPrice`, `PriceHistory`, `ScrapeLog`), détail de jeu très spécifique (`attacks`, `abilities`, `weaknesses`, `resistances`, `retreat`, `description`, `effect`), `predictedPrice` / `priceLowerBound` / `priceUpperBound` (retirés de `CARD`, cf. `docs/database/schema-sql.md`). Toute colonne ajoutée plus tard le sera par une migration additive du backend, annoncée au service TCG.
- **Seed** : `prisma/seed.ts` appelle `prisma/catalogue/SeedCatalogue.ts`, qui crée la licence Pokémon et les 3 sets de référence (`base1`, `swsh3`, `sv03.5` : 510 cartes, 1163 impressions) depuis `prisma/fixtures/tcgdex/` (réponses TCGdex en/fr, sans les prix). **Insert seulement** : une ligne qui existe déjà n'est jamais réécrite (`update: {}`) et rien n'est supprimé. Sinon relancer le seed sur une base rafraîchie par le service TCG y ramènerait les valeurs du snapshot du 2026-10-25 (défaut relevé par la revue). Le seed reste idempotent : mêmes lignes, mêmes UUID, mêmes dates (vérifié sur PostgreSQL). Pour récupérer de nouvelles fixtures en développement : `prisma migrate reset`, puis le seed. Les 3 sets sont un choix d'implémentation (le ticket ne les nomme pas) : en changer = modifier `REFERENCE_SET_IDS` et régénérer les fichiers (`fixtures/tcgdex/README.md`).
- **Attribution** : licence MIT de TCGdex conservée dans `prisma/fixtures/tcgdex/LICENSE` et citée dans `NOTICE.md` §5.
**Limites connues** :
- **Aucun index de recherche** (nom, trigrammes) : l'autocomplétion < 200 ms P95 est le périmètre de COLLR-418, qui choisira l'index (`pg_trgm` demande l'extension).
- **Tests de migration sans base** : `prisma/catalogue/CardCatalogueMigration.spec.ts` lit le SQL de la migration et fige les clés d'UPSERT (dont la clé composite des variantes), les FK, les colonnes FR/EN et l'absence de `CHECK` ; le CI du backend n'a pas de PostgreSQL (DevOps). `prisma/catalogue/CatalogueDatabase.spec.ts` rejoue l'essentiel contre un vrai PostgreSQL jetable : seed idempotent et insert seulement, upserts en SQL brut (version simplifiée des gabarits de `schema-sql.md`, pas une copie), contraintes, lecture du repository. Il est facultatif : ignoré sans `CATALOGUE_TEST_DATABASE_URL`, il refuse une base dont le nom ne contient pas `test` ou `check` comme mot, et une base qui contient autre chose que le catalogue seedé. La commande est dans l'en-tête du fichier.
- **Contraintes écrites à la main dans la migration** (Prisma ne sait pas les déclarer ; `prisma migrate diff` ne les voit pas, vérifié : aucune dérive) : colonnes liste `NOT NULL` (`types`, `dexIds`, `stamps`), pour qu'un `None` du service Python échoue au lieu de stocker un NULL que personne ne sait lire. **Aucun `CHECK`**, volontairement : deux `CHECK` de cohérence (série, évolution précédente) avaient été essayés puis retirés à la revue, parce que TCGdex peut fournir une série ou une évolution dans une seule langue, que la base aurait refusé la ligne et que le service aurait vu sa synchronisation bloquée. Le mapper est tolérant à la place (`LocalizedText.of(en ?? fr, fr)`). Même raison pour `officialCardCount <= totalCardCount` et `hp >= 0`.

## ADR-016 — Module `catalogue` : domaine et repository de lecture (COLLR-684)

Le ticket COLLR-684 a été étendu au domaine et à l'infrastructure de la partie carte : `src/modules/catalogue/` contient les entités, le port `ICardRepository` et son implémentation Prisma **en lecture seule**. Pas de use case ni de controller : ils sont dans COLLR-418 (recherche, autocomplétion) et COLLR-407, qui importent `CatalogueModule` (exporte le token `CARD_REPOSITORY`). L'écriture par lots relève d'un ticket Beta.
**Décisions** :
- **Entités du domaine** : `LicenceTCG`, `CardSet`, `Card`, `CardVariant`, toutes immuables et sans framework, avec une fabrique `restore` qui ne re-valide pas (la base est la source de vérité, même principe que `User.restore`). Pas de fabrique `create` : le backend n'écrit jamais dans le catalogue, il n'y a donc aucune règle de création à porter. Le ticket parle de « Game » ; on garde **`LicenceTCG`** (CDC, `schema-sql.md`, table `licences_tcg`) : à corriger dans Jira.
- **Une carte arrive avec son set, la licence du set et ses variantes** (`Card.set.licenceTCG`, `Card.variants`). Un résultat d'autocomplétion affiche le nom du set, et un élément de collection vise une variante : deux requêtes de plus par carte seraient pire qu'une jointure. Les listes sont bornées par la donnée (un set compte quelques centaines de cartes) et, pour la recherche, par `limit` (≤ 50) ; `findBySetId` ne l'est pas dans le code.
- **`LocalizedText` et `LocalizedUrl`** portent l'anglais et le français et gèrent le repli sur l'anglais (`in('fr')`). Les vocabulaires fixes (`category`, `rarity`, `types`, `stage`) restent des codes anglais traduits par le front (ADR-015).
- **Port `ICardRepository`** : `findById`, `findBySetId`, `searchByName`. Aucune méthode d'écriture. Un id qui n'est pas un UUID donne `null` / `[]` sans interroger la base (PostgreSQL lève sinon une erreur 500 pour un UUID mal formé).
- **`CardNameSearch`** (objet-valeur) valide la recherche avant la base : terme de 2 à 100 caractères, sans caractère de contrôle ni invisible, limite entière de 1 à 50 (20 par défaut). Erreur `InvalidCardSearchError`, que l'interface de COLLR-418 pourra convertir en 4xx ; son message ne reprend jamais le terme.
- **Recherche** : `contains` insensible à la casse sur `nameEn` **et** `nameFr`, tri par `nameEn` puis `tcgdexId` (deux recherches identiques donnent la même page). **Piège vérifié sur PostgreSQL** : Prisma ne protège pas `%` ni `_` dans `contains` ; sans échappement, `%%` ou `__` renvoyaient tout le catalogue. Le repository échappe `\`, `%` et `_` avant la requête.
- **Domaine volontairement mince** : la revue a fait retirer `completionOf`, `isTranslatedIn`, `isFirstEdition` et `abbreviationIn` (aucun appelant ; `completionOf` figeait en plus une règle de collection qui relève de COLLR-406/419). Reste `Card.findVariant`, parce que la règle « une variante appartient toujours à une carte » est écrite dans `documentation-metier.md` (règle transversale `cardId` / `variantId`) et que l'ajout à la collection (COLLR-419) doit la vérifier. Elle cherche par l'**`id` de la variante** (`variants.id`, ce que pointera un élément de collection ou une wishlist), jamais par le `variantId` TCGdex, qui n'a de sens qu'avec une carte (corrigé au troisième tour de revue).
- **`findBySetId` prend l'UUID du set, pas son id TCGdex** : `findBySetId('swsh3')` donne une liste vide, comme pour un set inconnu. À savoir pour COLLR-418 et COLLR-407.
- **Une recherche renvoie des cartes, pas des noms distincts** : l'autocomplétion montrera plusieurs « Pikachu » (un par set), sans classement par pertinence ni décalage. C'est le choix du classement, des doublons et de la pagination qui revient à COLLR-418, et le port changera probablement alors.
- **Ordre des cartes d'un set** : le numéro est du texte (`10` se trie avant `9` en SQL). `Card.compareByNumber` (collation numérique) l'ordonne dans le repository : `1, 2, 006, 10, 100, TG01`.
**Limites connues** :
- **La recherche ne neutralise pas les accents** (pas d'extension `unaccent` en base) : « dracaufeu » trouve « Dracaufeu », mais « Ecarlate » ne trouve pas « Écarlate ». Elle ne cherche que dans le nom, ni le numéro ni l'extension (le CDC parle d'autocomplétion sur les trois). Le choix de l'index (`pg_trgm`, `unaccent`) et le classement par préfixe sont dans COLLR-418.
- **Pas de pagination par curseur** : `searchByName` est borné par `limit` sans décalage. Une liste infinie demandera un `offset` ou un curseur, à décider avec le front.
- **Aucune donnée n'est copiée dans le domaine pour les images** : seules les URL de base du CDN TCGdex sont exposées (`Card.imageBaseUrlIn`), le front ajoute `/low.webp` ou `/high.webp`.

## ADR-017 — Module Collection : agrégat, port atomique, propriété, pagination, frontières domaine/infra (COLLR-416)

Module `src/modules/collection/` (`domain/` + `application/`, sans infrastructure ni endpoint : COLLR-417 les branche). Numéro 017 : le catalogue (COLLR-684) a pris le 015 et le 016. Relu par une revue senior adversariale le 2026-11-06 ; ce qui en a été retenu est marqué *(revue)*.
**Décisions** :
- **`CardEntry` est séparée de `Collection`.** Une collection monte à 10 000 entrées (CDC §3.1.3) : elle ne les contient pas, elles se lisent page par page via le repository (`PageRequest` → `Page<T>`, 50 par défaut, 100 max, une page invalide est rejetée plutôt que corrigée). La liste des collections, elle, n'est pas paginée : 10 au maximum par utilisateur. Un seul port, `ICollectionRepository`, pour les deux : une entrée n'existe que dans sa collection, et chaque opération sur une entrée est bornée par `collectionId`.
- **Écritures atomiques et ciblées, pas de `save` « insert ou update »** *(revue)*. `create(collection, maxPerUser)` compte et insère sous verrou du propriétaire (le plafond de 10 ne peut pas être dépassé par deux créations simultanées) ; `rename` n'écrit que le nom et ne recrée jamais une collection supprimée ; `addCardEntry` insère seulement ; `updateCardEntry(collectionId, entryId, changes)` n'écrit **que les champs fournis**, n'insère jamais et rejette `CardEntryNotFoundError` si l'entrée a disparu ; `deleteCardEntry` rejette aussi si elle est absente. Raisons : un upsert ressuscite une collection ou une entrée supprimée en parallèle ; une mise à jour qui relit puis réécrit toute la ligne annule silencieusement une modification concurrente (desktop et mobile ouverts ensemble) ; une mise à jour champ par champ garde en plus intactes les colonnes que le domaine ne modélise pas (`gradingResultId`). Pas de colonne `version` comme dans `auth` : des champs disjoints ne se gênent pas, l'écriture simultanée du même champ est « dernier arrivé gagne ».
- **Propriété vérifiée à un seul endroit** : `findOwnedCollection` (tous les use cases qui reçoivent un id de collection y passent). Une collection absente et celle d'un autre utilisateur donnent la **même** `CollectionNotFoundError` (IDOR, S03 §5.3) ; l'`userId` vient toujours de la session, jamais du body. C'est une convention, pas une impossibilité de construction : un nouveau use case qui appellerait `findById` directement la contournerait, ce que la revue de code doit attraper.
- **Identifiants validés comme UUID par le domaine** *(revue)* : `assertUuid` lève `DomainValidationError` (400) pour un id de collection, d'entrée, de carte, de variante ou de licence mal formé. Sans cela une valeur non UUID atteindrait une colonne `@db.Uuid` et donnerait une erreur PostgreSQL, donc un 500. Les lectures du port répondent `null` / page vide pour un id qui ne correspond à rien, sans lever.
- **Le domaine ne connaît pas le catalogue.** Il ne peut donc pas vérifier qu'une carte existe, qu'elle appartient à la licence de la collection, ni qu'une variante est une impression de cette carte. Ces garanties sont des **obligations du port** (`CardNotFoundError`, `LicenceNotFoundError`, `CollectionNotFoundError`), vérifiées par la suite de contrat. *(revue)* Une clé étrangère simple sur `variantId` ne prouve que l'existence de la variante, pas qu'elle appartient à `cardId` : il faut une clé étrangère composite `(cardId, variantId)` → `variants(cardId, id)` (donc un `UNIQUE (cardId, id)` sur `variants`, absent du schéma du catalogue mergé, qui n'a que `UNIQUE (cardId, tcgdexVariantId)` : à ajouter par la migration de COLLR-417) ou un contrôle explicite dans la même transaction.
- **`CardEntry` porte** : quantité (entier 1–9999), état déclaré (`NM`/`LP`/`MP`/`HP`/`DMG`), langue (`fr`/`en`), note de gradage (0–10 **avec au plus une décimale** *(revue)*, donc une colonne `decimal(3,1)` stocke exactement la valeur validée), notes libres (≤ 500 caractères, nullable), `addedAt`. Carte et variante sont **immuables** : se tromper de carte = supprimer l'entrée et en ajouter une autre. `condition` et `language` sont reçus en `string` et validés par le domaine (un appelant ne peut pas contourner la règle par un cast). Les longueurs sont comptées en caractères, pas en unités UTF-16, et les caractères invisibles (y compris les remplisseurs Hangul et le braille vide) sont refusés *(revue)*.
- **Le catalogue stocke `nameFr` / `nameEn`** (COLLR-684) : la langue de l'entrée désigne la carte physique et son prix, pas le texte affiché ; les codes `condition` restent neutres, traduits par clés côté front.
- **Pas de fusion** : deux ajouts de la même carte donnent deux entrées. **10 collections par utilisateur** au maximum (`MAX_COLLECTIONS_PER_USER`), toutes licences confondues, plusieurs par licence permises.
- **Erreurs** : `DomainValidationError` (copie locale, comme `auth`) est la seule erreur convertible en 400 ; les `*NotFoundError` et `CollectionLimitReachedError` ont un message fixe qui ne reprend aucune valeur reçue. Une mise à jour qui ne change rien est refusée (`At least one field must be changed`).
- **Contrat de comportement exécutable** *(revue)* : `src/contracts/CollectionPorts.contract.ts` + `InMemoryCollectionRepository.ts`, sur le modèle de `AuthPorts.contract.ts`. Les rejets typés, la non-résurrection, le plafond sous 15 créations simultanées, l'absence de mise à jour perdue et la pagination y sont testés. COLLR-417 doit exécuter **cette même suite** contre Prisma.
**Décisions produit tranchées** : 10 collections par utilisateur, plusieurs par licence, pas de fusion, langues `fr`/`en`, états NM→DMG, note de gradage 0–10. Les bornes techniques (quantité 1–9999, nom 1–60, notes 500, pages 50/100) sont dans `domain/rules/CollectionLimits.ts`, modifiables en une ligne.
**Plafond d'entrées par collection : reporté (décision du 2026-11-06).** Le CDC cite 10 000 comme capacité à supporter, pas comme limite, et le catalogue n'est pas encore complet : aucun plafond n'est imposé pour l'Alpha. Conséquence assumée : un utilisateur authentifié peut insérer un nombre non borné de lignes, seul le limiteur global (100 requêtes par minute) s'applique, et chaque ajout crée une entrée puisqu'il n'y a pas de fusion. À reprendre avec le catalogue complet : un `addCardEntry(entry, maxPerCollection)` atomique, sur le modèle du plafond de 10 collections (`create`), avec une constante dans `CollectionLimits.ts` et une erreur dédiée.
**Question produit encore ouverte** : une langue `fr` pour une carte dont `nameFr` est vide dans le catalogue est acceptée aujourd'hui.
**Documentation alignée** : `schema-sql.md` et `documentation-metier.md` décrivaient `COLLECTIONITEM` comme une carte physique unique (sans quantité, langue, notes ni date d'ajout) ; l'entité s'appelle désormais `CARDENTRY` (table `card_entries`) et porte les colonnes du ticket et du CDC §3.1.3–3.1.4. `gradingResultId` est conservé (nullable) mais pas exposé par le domaine. Le merge avec COLLR-684, qui modifiait les mêmes paragraphes de ces deux fichiers, a été résolu en gardant `CARDENTRY`.
**Réalisé par COLLR-417** (infrastructure et API, 2026-11-06) :
- **Tables** `collections` et `card_entries` (migration `20261106120000_add_collections`) : enums PostgreSQL `CardCondition` / `CardLanguage`, `card_entries.gradingNote` en `decimal(3,1)`, `gradingResultId` nullable sans clé étrangère (la table de notation n'existe pas encore). `collections.userId` → `users` en `ON DELETE CASCADE` (suppression de compte RGPD), `licenceTCGId` → `licences_tcg` en `RESTRICT`, `card_entries.collectionId` en `CASCADE` (la suppression d'une collection emporte ses entrées en une seule instruction, donc atomiquement), `cardId` en `RESTRICT`.
- **Clé étrangère composite** `card_entries(cardId, variantId)` → `variants(cardId, id)`, avec `UNIQUE (cardId, id)` ajouté sur `variants` : une variante appartient forcément à sa carte (`variantId` null ⇒ contrainte non vérifiée, `MATCH SIMPLE`). Deux `CHECK` de cohérence seulement (`quantity >= 1`, `gradingNote` entre 0 et 10) ; les bornes hautes restent dans le domaine pour ne pas diverger quand `CollectionLimits.ts` change.
- **`PrismaCollectionRepository`** : `create` prend `SELECT … FOR NO KEY UPDATE` sur la ligne du propriétaire (donc 15 créations simultanées → exactement 10 gagnent), puis vérifie la licence et compte avant d'insérer. `addCardEntry` pose `FOR SHARE` sur la collection (elle ne peut pas être supprimée avant le commit de l'entrée), vérifie la carte **et sa licence** (`CardNotFoundError` si la carte est d'une autre licence : une clé étrangère ne peut pas le prouver) puis la variante ; les violations de clé étrangère sont le filet de sécurité (`ForeignKeyViolation.ts`, détectées par nom de contrainte). `updateCardEntry` n'écrit que les champs fournis (`gradingResultId` survit, deux modifications de champs différents ne s'annulent pas). `rename` / `updateCardEntry` utilisent `update` (jamais d'insertion : pas de résurrection), `delete` utilise `deleteMany` (pas d'erreur si déjà supprimée).
- **Nom unique par propriétaire** (`@@unique([userId, name])`, migration `20261113120000_unique_collection_name_per_user`, COLLR-688) : index `collections_userId_name_key`, comparaison exacte (sensible à la casse, nom déjà rogné par le domaine). C'est l'index qui garantit la règle ; le repository traduit le `P2002` en `CollectionNameAlreadyUsedError` (409), à la création comme au renommage (renommer vers son propre nom n'est pas un conflit). La migration suffixe `" (2)"`, `" (3)"`… les doublons déjà présents (le plus ancien garde son nom) au lieu d'échouer.
- **Index** `card_entries(collectionId, addedAt DESC, id DESC)` (celui de `findCardEntries`) et `collections(userId, createdAt DESC, id DESC)`. `EXPLAIN` sur 10 000 entrées vérifié par un test d'intégration : le plan lit cet index, sans étape de tri ni lecture séquentielle.
- **Modèle de lecture** : port `ICardEntryViewReader` (dans `application/ports/`, séparé de `ICollectionRepository`) et `PrismaCardEntryViewReader` : une seule requête joint l'entrée, la carte, son extension et la variante (pas de requête par ligne). `ListCollectionCardsUseCase` vérifie la propriété puis lit. **Pas de prix** : aucune table de prix n'existe encore ; il rejoindra cette vue, pas le domaine.
- **API** (`CollectionsController`, `JwtAuthGuard`, `Cache-Control: no-store` sur les lectures, tag Swagger `Collections`) : `POST/GET /collections`, `GET/PATCH/DELETE /collections/:id`, `GET/POST /collections/:id/cards`, `PATCH/DELETE /collections/:id/cards/:entryId`. `DELETE /collections/:id` est tracé par `@Audit({ action: 'collection.delete', targetType: 'collection', targetIdParam: 'id' })` (succès et échec). Corps refusés au-delà des champs déclarés (`forbidNonWhitelisted`) : un `userId` dans le corps donne 400. `MapCollectionError` convertit `DomainValidationError` (celui du module) → 400, `*NotFoundError` → 404, `CollectionLimitReachedError` → 409 ; toute autre erreur reste un 500 générique.
- **Tests** : la suite de contrat passe contre PostgreSQL (`CollectionPorts.contract.integration-spec.ts`, `npm run test:integration`) avec les cas que seule une vraie base prouve (clé composite, `CHECK`, `gradingResultId`, plan d'exécution) ; specs unitaires (repository avec Prisma doublé, lecteur, mapper d'erreurs, DTO, contrôleur) ; e2e `test/collection/` (55 tests, `createAuthTestApp` accepte maintenant `overrides`).
**Reste, hors COLLR-417** : plafond d'entrées par collection (reporté, voir plus haut) ; prix dans la vue (en attente d'une table de prix) ; mutualiser `DomainValidationError` avec `auth` dans `shared/` (aujourd'hui deux classes, d'où un mapper par module) ; **partage 417 / 419** : `POST /collections/:id/cards` existe déjà ici (le ticket demande `/collections/:id/cards` en CRUD) alors que COLLR-419 décrit l'ajout à la collection avec la même validation, à trancher par le responsable des deux tickets.
