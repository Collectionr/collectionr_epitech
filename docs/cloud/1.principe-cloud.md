# Documentation d’Architecture, DevOps et Gouvernance — Projet ESP

## 1. Introduction

Ce document décrit de manière claire et structurée l’architecture, les choix DevOps, les principes de gouvernance ainsi que les bonnes pratiques de sécurité et de protection des données du projet **ESP**. L’objectif est de fournir une vision globale, cohérente et compréhensible, tout en justifiant les choix techniques et organisationnels.

---

## 2. Principes d’Architecture

### 2.1 Haute Disponibilité

La plateforme vise une disponibilité élevée et une reprise rapide en cas d’incident.
Dans le cadre du projet (ressources étudiantes), l’objectif est d’assurer :

 - redémarrage automatique des services (frontend/backend/workers),

 - monitoring (santé, logs, alerting),

 - sauvegardes régulières de la base de données et procédure de restauration testée.

La haute disponibilité de la base de données est assurée via un service managé ou, à défaut, par une stratégie backup/restore avec des objectifs de reprise (RPO/RTO) définis.

---

### 2.2 Scalabilité

Le frontend et le backend sont conçus stateless afin de permettre une scalabilité horizontale (ajout/suppression d’instances) selon la charge.
La base de données est dimensionnée pour le MVP via une approche verticale (ressources machine + optimisation : index, pooling). 
Des évolutions (read replicas / partitionnement) pourront être envisagées si la charge augmente.

---

### 2.3 Résilience

Les traitements lourds (scan par page, pré-grading IA, enrichissement) sont découplés via une file d’attente et des workers.
Cette approche :

 - absorbe les pics de charge,
 - protège l’API,
 - permet une mise à l’échelle indépendante des workers,
 - améliore la stabilité globale.

---

## 3. DevOps et Infrastructure

### 3.1 Choix d’Infrastructure

L'hébergement de l'infrastructure du projet ESP repose sur une approche de conteneurisation stricte. Cette stratégie garantit une isolation forte des composants, une reproductibilité des environnements et une indépendance totale vis-à-vis du fournisseur d'infrastructure (approche agnostique).

#### Phase MVP : Conteneurisation rigoureuse sous Docker

Pour le déploiement du MVP, l'infrastructure s'appuie sur une exécution conteneurisée orchestrée via **Docker Compose**. Cette approche permet de déployer rapidement l'ensemble de la stack (Frontend, API Node.js, Services IA Python, Base de données) tout en maîtrisant finement l'architecture locale.

Une attention particulière est portée sur la **configuration des conteneurs** dès cette première phase :
* Création d'images optimisées et sécurisées (*multi-stage builds*, images minimalistes).
* Isolation réseau stricte (création de réseaux virtuels dédiés pour que l'API Python et la base de données ne soient jamais exposées directement sur l'extérieur).
* Gestion maîtrisée des volumes persistants et des variables d'environnement.

Ce socle technique solide et standardisé est un prérequis indispensable pour faciliter la transition vers un orchestrateur plus avancé.

#### Évolution : Orchestration avec K3s

Pour accompagner la maturation du projet, la montée en charge et la complexification des traitements distribués, l'architecture a vocation à évoluer vers un cluster Kubernetes en utilisant **K3s**. 

K3s a été retenu car il s'agit d'une distribution Kubernetes certifiée, allégée et optimisée pour des environnements où l'empreinte ressource doit être maîtrisée. Cette évolution technique permettra d'apporter :
* **Haute disponibilité et résilience :** Redémarrage automatique des conteneurs défaillants (*auto-healing*).
* **Scalabilité :** Mise à l'échelle horizontale des pods (notamment pour les traitements IA) en fonction de la charge.
* **Déploiement avancé :** Mise à jour des services sans interruption (*rolling updates*) et gestion unifiée de la configuration via des manifestes Kubernetes.


---

### 3.2 CI/CD : GitHub Actions vs GitLab CI

Pour l’intégration et le déploiement continus, deux solutions sont envisagées.

**GitHub Actions** est simple à configurer et s’intègre très bien avec GCP. Il est parfaitement adapté aux pipelines standards.

**GitLab CI**, quant à lui, est plus puissant pour des pipelines complexes. Il est souvent privilégié en entreprise grâce à sa gestion intégrée des conteneurs et de l’infrastructure.

---

### 3.3 Automatisation : Terraform

L’automatisation est indispensable pour garantir la fiabilité des déploiements et éviter les problèmes classiques de type « ça marchait sur mon PC ». Pour ce faire, le projet s'appuie exclusivement sur une approche d'**Infrastructure as Code (IaC)**.

**Terraform** est l'unique outil utilisé pour décrire et provisionner l'infrastructure. Ses avantages pour le projet sont multiples :
* **Provisionnement unifié :** Il permet de créer et configurer le serveur hôte (VPS/VM) ainsi que les règles de sécurité réseau (pare-feu, ouverture stricte des ports) de manière automatisée.
* **Traçabilité et Reproductibilité :** L'état de l'infrastructure est défini sous forme de code. Grâce à l'historique Git, il est possible d'auditer chaque changement, de restaurer l'infrastructure en une seule commande en cas de crash, ou de dupliquer facilement un environnement (développement, production).
* **Infrastructure Immuable :** Le choix de se passer d'outils de gestion de configuration classique (comme Ansible) s'explique par notre utilisation stricte de Docker. Les dépendances et la configuration applicative sont encapsulées directement dans les images conteneurisées. Le serveur hôte reste ainsi minimaliste, et les mises à jour sont gérées par la CI/CD qui déploie de nouveaux conteneurs plutôt que de modifier un serveur existant.

> **Note de conformité :** Afin de respecter les contraintes de souveraineté des données (Privacy by Design), toutes les ressources provisionnées par Terraform doivent obligatoirement être déployées dans une région européenne.

> Toutes les ressources doivent être déployées dans la région **europe-westX**, imposée dans le code Terraform.

## 4. Gouvernance du Projet

### 4.1 Séparation des Responsabilités

La gouvernance du projet repose sur une séparation claire des rôles.

#### **A. Pôle Infrastructure (Le Bâtisseur)**
*Responsable de la disponibilité, de la performance et de l'automatisation.*

* **Architecture & Réseau :** Conception du VPC, gestion des sous-réseaux, du routage et des règles de pare-feu (Firewall) pour exposer les services.
* **Infrastructure as Code (IaC) :** Développement et maintenance des scripts **Terraform**. Garant de l'état "souhaité" de l'infrastructure.
* **Usine de Déploiement (CI/CD) :** Création et optimisation des pipelines **GitHub Actions**. Objectif : fournir un déploiement rapide et fiable (Build -> Test -> Deploy).
* **Standardisation des Conteneurs :** Définition des standards Docker (images légères `alpine`/`distroless`, *multistage builds*). Ce travail technique prépare la migration future vers l'orchestrateur **K3s**.
* **Monitoring :** Mise en place des tableaux de bord (Cloud Monitoring) pour surveiller la santé des services.

#### **B. Pôle Cyber-Sécurité (Le Gardien)**
*Responsable de la protection des données, des identités et de la conformité.*

* **Gestion des Identités (IAM) :** Création des comptes de service et application stricte du principe de **Moindre Privilège** (chaque service n'a accès qu'à ce qui lui est strictement nécessaire).
* **Audit Automatisé :** Intégration d'outils de sécurité dans la CI/CD (scan de vulnérabilités des images Docker via Trivy, analyse statique du code).
* **Gestion des Secrets :** Administration de **Google Secret Manager**. Garantie qu'aucun mot de passe ou clé API n'est visible dans le code (Git) ou les variables d'environnement en clair.
* **Tests & Revue :** Validation systématique des *Pull Requests* d'infrastructure pour vérifier l'absence de failles de sécurité dans la configuration (misconfiguration).
---

### 4.2 Principe de Traçabilité

Toute modification d’infrastructure passe par le principe d’**Infrastructure as Code**. Chaque changement est versionné via Git, ce qui garantit une traçabilité complète.

Les **journaux d’activité** sont systématiquement activés afin de tracer les accès aux données et les modifications de configuration.

Les **modèles d’intelligence artificielle** sont versionnés par l’équipe Data afin de garantir la reproductibilité des résultats à un instant donné.

---

### 4.3 Gouvernance des Flux et des Données

La base de données PostgreSQL est strictement isolée et n’accepte que des connexions provenant de l’API Node.js.

Les services Python ne communiquent jamais directement avec la base de données. Ils passent par une **API interne Node.js**, ce qui centralise la logique métier et renforce la sécurité.

L’API Python est déployée dans un **sous-réseau privé (VPC)** accessible uniquement par l’API Node.

---

## 5. Sécurité et Protection des Données

### 5.1 Contexte GCP et Données Européennes

Le projet ESP utilise Google Cloud pour ses avantages en data et en intelligence artificielle. Cependant, la souveraineté des données impose que celles-ci soient **hébergées en Europe**. Il est nécessaire de vérifier les conditions générales afin de s’assurer que Google n’utilise pas les données pour entraîner ses propres modèles.

---

### 5.2 Security by Design

Chaque composant est conçu selon le **principe du moindre privilège**, avec uniquement les droits strictement nécessaires à son fonctionnement.

Les environnements sont séparés de manière stricte, à la fois logiquement et techniquement. Le réseau adopte une approche **Zero Trust**, où aucun composant n’est considéré comme fiable par défaut.

Les données sont systématiquement **chiffrées en transit et au repos**. Les secrets ne sont jamais stockés en clair dans le code. L’observabilité est intégrée dès la conception grâce à des logs, métriques et traces exploitables.

---

### 5.3 Privacy by Design

L’approche Privacy by Design repose sur la **minimisation des données**, la limitation des finalités, une durée de conservation définie et justifiée, ainsi que des paramètres de protection par défaut.

Chaque accès ou traitement de données personnelles est traçable et explicable. L’option **Access Approval** de GCP est recommandée afin de renforcer la transparence.

---

## 6. Gestion des Accès et IAM

Les accès sont strictement nominatifs et aucun compte n’est partagé. Les rôles sont attribués à des groupes et non à des individus.

Les équipes Cloud et Cyber sont les seules autorisées à modifier la configuration réseau. L’équipe Dev/Data dispose d’un accès en lecture sur la production et d’un accès développeur en sandbox. Aucune création manuelle de ressources n’est autorisée.

Les déploiements sont exclusivement réalisés par la **CI/CD via des comptes de service**.

---

## 7. Infrastructure Immuable

Toute l’infrastructure est décrite et gérée via Terraform. Les images Docker ou Kubernetes sont créées une seule fois, testées, puis déployées en production sans modification manuelle.

---

## 8. Traçabilité Globale

La traçabilité humaine repose sur des **pull requests obligatoires**, validées par un membre de l’équipe Cloud ou Cyber.

La traçabilité technique est assurée par **Cloud Audit Logs** et **VPC Flow Logs**, tandis que la traçabilité applicative repose sur la centralisation des logs via **Cloud Logging**.

---

## 9. Organisation et Flexibilité

Le chef de projet veille au respect des conventions de nommage et des tests. Chaque service dispose de sa propre documentation README.

Toutes les ressources cloud doivent inclure des **labels obligatoires**, tels que : `project: esp`, `env: dev|prod`, `team: data|dev|cloud`.

---

## 10. Modèle Cloud — Projet ESP

Google Cloud Platform est le choix privilégié pour le projet ESP. Il excelle dans la gestion de la data et de l’IA, propose une interface claire et s’intègre parfaitement avec la stack technique du projet.

Les services Node.js et Python sont conteneurisés. La communication asynchrone repose sur **Google Pub/Sub**, solution plus robuste qu’un simple appel HTTP.

La base de données PostgreSQL est hébergée sur **Cloud SQL**. En raison du nombre élevé de connexions générées par Prisma, un **pooler de connexions (PgBouncer)** est nécessaire. L’**Auth Proxy** de GCP est utilisé pour sécuriser les connexions.

---

## 11. Services et Déploiement

L’API Node.js est déployée sur un **PaaS**, car elle doit être disponible en permanence pour les utilisateurs.

Les traitements Python liés à l’IA sont déployés en **serverless** et s’exécutent uniquement lorsqu’une image est envoyée.

La base de données est consommée sous forme de **SaaS**. La communication entre Node et Python se fait via une API interne sécurisée, avec authentification inter-services.

Deux unités de déploiement distinctes sont gérées par la CI/CD.

---

## 12. Solutions Techniques Explorées

Les solutions étudiées pour le projet ESP incluent Google Cloud Run, Kubernetes (K3s ou GKE) et Docker sans orchestrateur.

À ce stade, une approche entièrement **dockerisée sans Kubernetes** est privilégiée afin de limiter la complexité, tout en conservant une possibilité d’évolution future.

---

## 13. Conclusion

Cette documentation définit une architecture robuste, sécurisée et évolutive pour le projet ESP. Les choix techniques et organisationnels visent à garantir la disponibilité, la conformité réglementaire et la maintenabilité du système, tout en laissant une marge d’évolution en fonction des besoins futurs.
