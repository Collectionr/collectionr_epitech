# 1. Introduction

Le projet **Collectionr** est développé par une équipe de 9 étudiants et a pour objectif de proposer une application fiable destinée aux collectionneurs de cartes TCG.

Cette documentation présente les principaux choix techniques et organisationnels du projet. L'objectif est de construire une application robuste, sécurisée et évolutive tout en utilisant des outils reconnus dans l'industrie.

L’architecture repose sur plusieurs principes :

- Une infrastructure conteneurisée pour faciliter le déploiement.
- Une automatisation des tâches de développement et de livraison.
- Une protection des données intégrée dès la conception.
- Une organisation claire des responsabilités au sein de l’équipe.

---

# 2. Principes d’Architecture

## 2.1 Disponibilité

L’objectif n’est pas d’atteindre une disponibilité parfaite, mais de garantir une application stable et fiable.

Pour cela :

- Les services redémarrent automatiquement en cas de problème.
- Les erreurs et incidents peuvent être détectés rapidement grâce aux mécanismes de surveillance.

👉 Résultat :

L’application reste accessible même lorsqu’un composant rencontre une difficulté temporaire.

---

## 2.2 Scalabilité

L’application est conçue pour pouvoir accueillir davantage d’utilisateurs si son utilisation augmente.

- Le Frontend et le Backend peuvent être répliqués pour absorber davantage de trafic.
- La base de données est pensée pour gérer une croissance progressive du volume de données.

👉 Résultat :

Le projet peut évoluer sans nécessiter une refonte complète de l’architecture.

---

## 2.3 Résilience et isolation

L’architecture cherche à éviter qu’un problème local ne provoque une panne générale.

Pour cela :

- Les traitements lourds (IA, OCR, récupération de données externes) sont exécutés de manière asynchrone via Redis.
- Les données importantes restent disponibles même si un service secondaire rencontre un problème.
- Les images et fichiers volumineux sont stockés séparément de la base de données principale.

👉 Résultat :

Les incidents restent isolés et n’impactent pas l’ensemble de l’application.

# 3. DevOps et Infrastructure

## 3.1 Stack technique

Le projet s’appuie sur des technologies largement utilisées dans le développement moderne.

| Domaine | Technologie |
|----------|-------------|
| Frontend | React / React Native + TypeScript |
| Backend | Node.js / NestJS |
| Intelligence Artificielle | Python (OpenCV, YOLO) |
| Données | PostgreSQL + Redis |
| Orchestration | K3s |
| File d'attente | Redis |
| Stockage | Volumes persistants |
| Gestion des secrets | Vault ou Doppler |
| CI/CD | GitHub Actions |

### Évolution de l’infrastructure

K3s est utilisé comme orchestrateur principal dès le démarrage du projet.

Docker reste utilisé pour construire les images des différents services.

Docker Compose peut être utilisé localement pour certains tests ou phases de développement, mais ne fait pas partie de l’architecture cible.

---

## 3.2 Automatisation

Afin de réduire les erreurs humaines, plusieurs tâches sont automatisées.

- Les tests sont exécutés automatiquement.
- Les images applicatives sont générées automatiquement.
- Les déploiements suivent un processus standardisé.

👉 Résultat :

Le projet reste reproductible et plus simple à maintenir.

---

## 3.3 Bonnes pratiques Cloud

Pour garantir la stabilité et la maîtrise des coûts, plusieurs principes sont appliqués :

### Infrastructure as Code

L’infrastructure est décrite dans du code afin de pouvoir être recréée facilement et de limiter les interventions manuelles.

### Séparation des environnements

Les environnements de développement, de test et de production sont isolés les uns des autres.

### Gestion des coûts

Les ressources utilisées sont surveillées afin d’éviter les dépenses inutiles.

### Observabilité

Des mécanismes de suivi permettent de surveiller l’état du système et de détecter rapidement les anomalies.

👉 Résultat :

L’infrastructure reste contrôlée, prévisible et plus facile à faire évoluer.

# 4. Gouvernance et Sécurité

## 4.1 Organisation des rôles

Les responsabilités sont réparties entre plusieurs domaines :

### Infrastructure

Responsable des serveurs, du déploiement et du maintien en condition opérationnelle.

### Sécurité

Responsable de la protection des accès, des secrets et des données.

---

### Gestion des accès (IAM)

Les accès aux outils et aux infrastructures sont strictement contrôlés.

- Chaque membre possède son propre compte.
- Aucun compte partagé n’est utilisé.
- Les permissions accordées sont limitées au strict nécessaire.

👉 Résultat :

Les actions sont traçables et les risques liés aux accès excessifs sont réduits.

---

## 4.2 Protection des données

La sécurité et la confidentialité sont prises en compte dès la conception du projet.

### Sécurité dès la conception

Les mécanismes de sécurité sont intégrés directement dans l’architecture :

- Chiffrement des communications.
- Protection des secrets.
- Respect des bonnes pratiques de développement sécurisé.

### Protection de la vie privée

Les données personnelles sont prises en compte dès le développement de l’application.

### Minimisation des données

Seules les informations réellement nécessaires au fonctionnement du service sont collectées.

### Paramètres protecteurs par défaut

Les paramètres de confidentialité sont configurés au niveau le plus protecteur dès la création d’un compte.

### Contrôle et traçabilité

Les accès aux données sensibles sont limités, contrôlés et peuvent être audités.

👉 Résultat :

Les données des utilisateurs sont protégées et le projet respecte les exigences réglementaires applicables.

---

# 5. Déploiement automatique (CI/CD) et Traçabilité

Le cycle de livraison est automatisé afin de garantir des mises à jour fiables.

Le processus comprend :

1. Vérification de la qualité du code.
2. Analyse de sécurité.
3. Construction des images applicatives.
4. Déploiement sur l’infrastructure.

---

## Gestion des Pull Requests

Toute modification du projet doit passer par une Pull Request.

Avant son intégration :

- Le code doit être relu.
- Les tests doivent être validés.
- Un autre membre de l’équipe doit approuver les changements.

👉 Résultat :

Chaque évolution est contrôlée, documentée et peut être retracée facilement.

---

# 6. Conclusion

Cette architecture permet de :

- Construire une application fiable.
- Automatiser les tâches importantes.
- Sécuriser les données et les accès.
- Faciliter la maintenance du projet.
- Préparer les futures évolutions.

### Perspectives d’évolution

L’architecture repose aujourd’hui sur K3s afin de rester simple et légère.

Si les besoins augmentent fortement dans le futur, elle pourra évoluer vers une infrastructure Kubernetes plus complète sans remettre en cause les fondations actuelles.

👉 En résumé :

Collectionr repose sur une architecture moderne, sécurisée et évolutive, adaptée à un projet étudiant tout en s’inspirant des pratiques professionnelles utilisées en entreprise.
