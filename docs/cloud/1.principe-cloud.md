# Documentation d’Architecture, DevOps et Gouvernance — Projet ESP

## 1. Introduction

Ce document décrit de manière claire et structurée l’architecture, les choix DevOps, les principes de gouvernance ainsi que les bonnes pratiques de sécurité et de protection des données du projet **ESP**. L’objectif est de fournir une vision globale, cohérente et compréhensible, tout en justifiant les choix techniques et organisationnels.

---

## 2. Principes d’Architecture

### 2.1 Haute Disponibilité

La plateforme vise une disponibilité élevée et une reprise rapide en cas d’incident.
Dans le cadre du projet (ressources étudiantes), l’objectif est d’assurer :

 - redémarrage automatique des services (frontend/backend/workers),

 - monitoring (santé, logs, alerting),

 - sauvegardes régulières de la base de données et procédure de restauration testée.

La haute disponibilité de la base de données est assurée via un service managé ou, à défaut, par une stratégie backup/restore avec des objectifs de reprise (RPO/RTO) définis.

---

### 2.2 Scalabilité

Le frontend et le backend sont conçus stateless afin de permettre une scalabilité horizontale (ajout/suppression d’instances) selon la charge.
La base de données est dimensionnée pour le MVP via une approche verticale (ressources machine + optimisation : index, pooling). 
Des évolutions (read replicas / partitionnement) pourront être envisagées si la charge augmente.

---

### 2.3 Résilience

# Architecture — Gestion des flux et performance

Afin de garantir une haute disponibilité et une réactivité optimale de l'interface, l'architecture repose sur un découplage strict des flux transactionnels et des traitements asynchrones :

## Isolation des bases de données

Une distinction nette est opérée entre la base de données de production (Backend) et la base dédiée au stockage et au traitement de l'IA. Cette séparation garantit que les requêtes intensives de la partie Data (extractions massives, entraînements, calculs) n'impactent jamais les performances des opérations transactionnelles des utilisateurs.

## Système de file d'attente (Redis)

Les traitements lourds (scan par page, pré-grading IA, enrichissement) sont gérés via une file d'attente pilotée par Redis. Ce mécanisme de Message Broker permet de distribuer les tâches aux workers de manière fluide et ordonnée.

## 3. DevOps et Infrastructure

### 3.1 Choix d’Infrastructure

L'hébergement de l'infrastructure du projet ESP repose sur une approche de conteneurisation stricte. Cette stratégie garantit une isolation forte des composants, une reproductibilité des environnements et une indépendance totale vis-à-vis du fournisseur d'infrastructure (approche agnostique).

#### Phase MVP : Conteneurisation rigoureuse sous Docker

Pour le déploiement du MVP, l'infrastructure s'appuie sur une exécution conteneurisée orchestrée via Docker Compose. Cette approche permet de déployer et de lier de manière fluide l'ensemble de la stack technique :

- Le Frontend (React/Next ou autre),

- L'API Node.js (Backend transactionnel),

- Les Services IA Python (Traitement de données),

- Les Bases de données isolées (PostgreSQL/MongoDB),

- Et Redis, agissant comme pivot pour la gestion des files d'attente asynchrones.

Une attention particulière est portée sur la **configuration des conteneurs** dès cette première phase :
* Création d'images optimisées et sécurisées (*multi-stage builds*, images minimalistes).
* Isolation réseau stricte (création de réseaux virtuels dédiés pour que l'API Python et la base de données ne soient jamais exposées directement sur l'extérieur).
* Gestion maîtrisée des volumes persistants et des variables d'environnement.

Ce socle technique solide et standardisé est un prérequis indispensable pour faciliter la transition vers un orchestrateur plus avancé.

#### Évolution : Orchestration avec K3s

Pour accompagner la maturation du projet, la montée en charge et la complexification des traitements distribués, l'architecture a vocation à évoluer vers un cluster Kubernetes en utilisant **K3s**. 

K3s a été retenu car il s'agit d'une distribution Kubernetes certifiée, allégée et optimisée pour des environnements où l'empreinte ressource doit être maîtrisée. Cette évolution technique permettra d'apporter :
* **Haute disponibilité et résilience :** Redémarrage automatique des conteneurs défaillants (*auto-healing*).
* **Scalabilité :** Mise à l'échelle horizontale des pods (notamment pour les traitements IA) en fonction de la charge.
* **Déploiement avancé :** Mise à jour des services sans interruption (*rolling updates*) et gestion unifiée de la configuration via des manifestes Kubernetes.


---

### 3.2 CI/CD : GitHub Actions vs GitLab CI

Pour l’intégration et le déploiement continus, deux solutions sont envisagées.

**GitHub Actions** est simple à configurer et s’intègre très bien avec GCP. Il est parfaitement adapté aux pipelines standards.

**GitLab CI**, quant à lui, est plus puissant pour des pipelines complexes. Il est souvent privilégié en entreprise grâce à sa gestion intégrée des conteneurs et de l’infrastructure.

---

### 3.3 Automatisation : Terraform

L’automatisation est indispensable pour garantir la fiabilité des déploiements et éviter les problèmes de type « ça marchait sur mon PC ». Le projet repose sur une approche IaC hybride, adaptée à notre architecture conteneurisée.

**Terraform** est l'unique outil utilisé pour décrire et provisionner l'infrastructure. Ses avantages pour le projet sont multiples :
* **Provisionnement unifié :** Il permet de créer et configurer le serveur hôte (VPS/VM) ainsi que les règles de sécurité réseau (pare-feu, ouverture stricte des ports) de manière automatisée.
* **Traçabilité et Reproductibilité :** L'état de l'infrastructure est défini sous forme de code. Grâce à l'historique Git, il est possible d'auditer chaque changement, de restaurer l'infrastructure en une seule commande en cas de crash, ou de dupliquer facilement un environnement (développement, production).
* **Infrastructure Immuable :** Le choix de se passer d'outils de gestion de configuration classique (comme Ansible) s'explique par notre utilisation stricte de Docker. Les dépendances et la configuration applicative sont encapsulées directement dans les images conteneurisées. Le serveur hôte reste ainsi minimaliste, et les mises à jour sont gérées par la CI/CD qui déploie de nouveaux conteneurs plutôt que de modifier un serveur existant.

> **Note de conformité :** Afin de respecter les contraintes de souveraineté des données (Privacy by Design), toutes les ressources provisionnées par Terraform doivent obligatoirement être déployées dans une région européenne.

> Toutes les ressources doivent être déployées dans la région **europe-westX**, imposée dans le code Terraform.

## 4. Gouvernance du Projet

### 4.1 Séparation des Responsabilités

La gouvernance du projet repose sur une séparation claire des rôles.

#### **A. Pôle Infrastructure (Le Bâtisseur)**
*Responsable de la disponibilité, de la performance et de l'automatisation.*

* **Architecture & Réseau :** Conception du VPC, gestion des sous-réseaux, du routage et des règles de pare-feu (Firewall) pour exposer les services.
* **Infrastructure as Code (IaC) :** Développement et maintenance des scripts **Terraform**. Garant de l'état "souhaité" de l'infrastructure.
* **Usine de Déploiement (CI/CD) :** Création et optimisation des pipelines **GitHub Actions**. Objectif : fournir un déploiement rapide et fiable (Build -> Test -> Deploy).
* **Standardisation des Conteneurs :** Définition des standards Docker (images légères `alpine`/`distroless`, *multistage builds*). Ce travail technique prépare la migration future vers l'orchestrateur **K3s**.
* **Monitoring :** Mise en place des tableaux de bord (Cloud Monitoring) pour surveiller la santé des services.

#### **B. Pôle Cyber-Sécurité (Le Gardien)**
*Responsable de la protection des données, des identités et de la conformité.*

* **Gestion des Identités (IAM) :** Création des comptes de service et application stricte du principe de **Moindre Privilège** (chaque service n'a accès qu'à ce qui lui est strictement nécessaire).
* **Audit Automatisé :** Intégration d'outils de sécurité dans la CI/CD (scan de vulnérabilités des images Docker via Trivy, analyse statique du code).
* **Gestion des Secrets :** Administration de **Google Secret Manager**. Garantie qu'aucun mot de passe ou clé API n'est visible dans le code (Git) ou les variables d'environnement en clair.
* **Tests & Revue :** Validation systématique des *Pull Requests* d'infrastructure pour vérifier l'absence de failles de sécurité dans la configuration (misconfiguration).
---

### 4.2 Principe de Traçabilité

Toute modification d’infrastructure passe par le principe d’**Infrastructure as Code**. Chaque changement est versionné via Git, ce qui garantit une traçabilité complète.

Les **journaux d’activité** sont systématiquement activés afin de tracer les accès aux données et les modifications de configuration.

Les **modèles d’intelligence artificielle** sont versionnés par l’équipe Data afin de garantir la reproductibilité des résultats à un instant donné.

---

### 4.3 Gouvernance des Flux et des Données

La gestion des flux réseau et des accès aux données au sein de l'infrastructure repose sur le principe de moindre exposition et de centralisation de la logique métier.

## Centralisation via Node.js (Gateway)

L'API Node.js agit comme l'unique point d'entrée du backend. Toutes les requêtes en provenance du Frontend sont réceptionnées par Node.js, qui orchestre la validation, l'authentification et la distribution des tâches.

---

## Communication Asynchrone via File d'Attente (Redis)

Contrairement à un modèle synchrone classique, les traitements lourds liés à l'intelligence artificielle sont gérés de manière asynchrone.

- L'API Node.js publie un "job" dans une file d'attente Redis.

- Les workers Python consomment ces messages dès qu'ils sont disponibles.

- Ce modèle évite les timeouts HTTP et permet à l'utilisateur de continuer à naviguer pendant que l'IA travaille en arrière-plan.

---

## Isolation Réseau Stricte (Docker Network)

Afin de garantir un haut niveau de sécurité, les services Python, l'instance Redis et la base de données PostgreSQL ne sont jamais exposés sur Internet. Aucun port public n'est ouvert pour ces composants. Ils communiquent exclusivement au sein d'un réseau virtuel privé interne à Docker. Le conteneur Node.js est le seul "pont" autorisé entre l'extérieur et ce réseau sécurisé.

---

## Protection de la Base de Données et Intégrité

La base de données PostgreSQL est confinée dans ce même réseau privé. Conformément au principe de moindre privilège, les services Python n'ont pas d'accès direct à la base de données transactionnelle.

- Une fois le traitement IA terminé, le worker Python communique le résultat à l'API Node.js (via Redis ou un callback interne).

- C'est l'API Node.js qui se charge d'effectuer les écritures finales en base, garantissant ainsi une centralisation totale des règles métier et de sécurité.

## 5. Sécurité et Protection des Données

### 5.1 Contexte GCP et Données Européennes

L'architecture du projet ESP est conçue pour être agnostique et portable, privilégiant l'utilisation d'un VPS indépendant pour l'hébergement de la stack technique (via Docker Compose). Ce choix permet de s'affranchir de la dépendance exclusive à un fournisseur unique et de respecter notre contrainte de budget.

Toutefois, pour les besoins spécifiques en Intelligence Artificielle et analyse de données, le projet pourra s'appuyer ponctuellement sur des services tiers (tels que ceux de Google Cloud via leurs offres gratuites ou APIs). Dans ce cas, une attention particulière est portée à la souveraineté des données :

- Le stockage restera localisé sur notre infrastructure ou sur des serveurs hébergés en Europe.

- Une vérification systématique des conditions générales sera effectuée pour garantir que les données du projet ne sont pas utilisées pour l'entraînement des modèles propriétaires de Google.


---

### 5.2 Security by Design

Chaque composant est conçu selon le **principe du moindre privilège**, avec uniquement les droits strictement nécessaires à son fonctionnement.

Les environnements sont séparés de manière stricte, à la fois logiquement et techniquement. Le réseau adopte une approche **Zero Trust**, où aucun composant n’est considéré comme fiable par défaut.

Les données sont systématiquement **chiffrées en transit et au repos**. Les secrets ne sont jamais stockés en clair dans le code. L’observabilité est intégrée dès la conception grâce à des logs, métriques et traces exploitables.

---

### 5.3 Privacy by Design

L’approche Privacy by Design repose sur la **minimisation des données**, la limitation des finalités, une durée de conservation définie et justifiée, ainsi que des paramètres de protection par défaut.

Chaque accès ou traitement de données personnelles est traçable et explicable. L’option **Access Approval** de GCP est recommandée afin de renforcer la transparence.

---

## 6. Gestion des Accès et IAM

Les accès sont strictement nominatifs et aucun compte n’est partagé. Les rôles sont attribués à des groupes et non à des individus.

Les équipes Cloud et Cyber sont les seules autorisées à modifier la configuration réseau. L’équipe Dev/Data dispose d’un accès en lecture sur la production et d’un accès développeur en sandbox. Aucune création manuelle de ressources n’est autorisée.

Les déploiements sont exclusivement réalisés par la **CI/CD via des comptes de service**.

---

## 7. Infrastructure Immuable

Toute l’infrastructure est décrite et gérée via Terraform. Les images Docker ou Kubernetes sont créées une seule fois, testées, puis déployées en production sans modification manuelle.

---

## 8. Traçabilité Globale

Dans le cadre de notre infrastructure auto-hébergée, la traçabilité est assurée par des processus de validation stricts et l'exploitation des journaux natifs des outils utilisés.

### 8.1 Traçabilité Humaine et Processus (GitOps)

La règle d'or du projet est la suivante : **aucune modification manuelle n'est autorisée sur le serveur de production**. Toute évolution (code applicatif ou infrastructure Terraform) suit un flux de travail rigoureux :
* **Pull Requests (PR) Obligatoires :** Les branches principales (`main`/`master`) sont protégées sur GitHub. Chaque modification doit faire l'objet d'une PR.
* **Revue par les Pairs :** Toute PR impactant l'infrastructure, la configuration réseau ou les variables d'environnement doit être obligatoirement relue et approuvée par au moins un membre du pôle **Cloud** ou **Cyber-Sécurité**.
* **Historique Git :** Ce fonctionnement garantit qu'il est toujours possible de savoir *qui* a fait *quelle* modification, *quand*, et *pourquoi* (grâce aux commentaires de PR).

### 8.2 Traçabilité Technique et Applicative

* **Traçabilité des Déploiements :** L'historique des exécutions de notre CI/CD (GitHub Actions) sert de journal d'audit technique pour les déploiements. Chaque build d'image ou exécution Terraform y est consigné avec son statut de réussite ou d'échec.
* **Traçabilité Applicative (Logs) :** En phase MVP, la centralisation des logs repose sur les flux standards des conteneurs (`stdout` et `stderr`). Les journaux sont capturés et consultables nativement via le démon Docker (`docker logs`). 
* **Évolution prévue :** Lors du passage vers l'orchestrateur K3s, une pile de journalisation légère (de type Grafana Loki ou ELK allégé) pourra être déployée pour centraliser et interroger plus facilement les logs de tous les pods.

## 10. Modèle d'Hébergement et Services

Le projet ESP s'affranchit des fournisseurs Cloud onéreux pour privilégier une approche **auto-hébergée (IaaS)** sur un Serveur Privé Virtuel (VPS). Ce choix permet de maîtriser totalement les coûts (adapté à un budget étudiant) tout en respectant la souveraineté des données (hébergement en Europe).

L'ensemble de la stack applicative est conteneurisé et orchestré via **Docker Compose** :
* **Base de données (PostgreSQL) :** Hébergée dans un conteneur dédié. La persistance des données est assurée par des volumes Docker (bind mounts ou named volumes) régulièrement sauvegardés. L'utilisation d'un pooler de connexions (comme PgBouncer) pourra être ajoutée en tant que conteneur indépendant si l'ORM Prisma sature les connexions de la base.
  
* **Gestionnaire de File d'Attente (Redis) :** Élément pivot de l'architecture, Redis est déployé en tant que conteneur pour assurer la communication asynchrone entre le backend Node.js et les services IA en Python. Il permet de stocker temporairement les tâches lourdes (scans, calculs) sous forme de messages, garantissant qu'aucune requête ne soit perdue même en cas de pic de charge.

* **Backend (Node.js) :** Agit en tant que service principal, constamment actif pour répondre aux requêtes des utilisateurs et interagir avec la base de données.
* **Workers IA (Python) :** Déployés sous forme d'API internes synchrones. Ils ne sont sollicités par Node.js que lors de la soumission d'une image ou d'un traitement spécifique.



## 11. Pipeline de Déploiement (CI/CD)

Le déploiement continu repose sur **GitHub Actions**, offrant une intégration native avec notre gestionnaire de code source sans générer de coûts supplémentaires.

Le pipeline de déploiement suit une logique d'intégration stricte :
1. **Build & Test :** À chaque *Push* ou *Pull Request* sur la branche principale, le code est testé, analysé (linting, scan de vulnérabilités Trivy) et les images Docker sont construites.
2. **Registry :** Les images validées sont poussées vers un registre de conteneurs privé (ex: GitHub Container Registry - GHCR).
3. **Déploiement Automatisé :** L'agent GitHub Actions se connecte de manière sécurisée (via clé SSH stockée dans les secrets GitHub) au VPS de production. Il télécharge les nouvelles images (`docker pull`) et redémarre les services concernés sans interruption globale (`docker compose up -d`).

Aucune compilation de code n'est effectuée sur le serveur de production, respectant ainsi le principe d'infrastructure immuable.

## 12. Conclusion et Évolutivité

Cette documentation définit une architecture pragmatique, robuste et parfaitement alignée avec les contraintes financières et temporelles du projet ESP. 

Le choix de démarrer avec une **infrastructure dockerisée centralisée (VPS + Docker Compose)** permet à l'équipe de se concentrer sur le développement du MVP et la création de valeur (l'IA et les fonctionnalités), sans se noyer dans la complexité opérationnelle d'un orchestrateur complet dès les premiers mois.

Cette architecture n'est cependant pas figée. La conteneurisation stricte et l'automatisation via Terraform et GitHub Actions constituent un socle technique idéal. Dès que le projet nécessitera une haute disponibilité poussée ou une distribution de la charge (notamment pour les traitements IA intensifs), l'infrastructure pourra naturellement pivoter vers un cluster **K3s**, garantissant ainsi la pérennité et la scalabilité du projet ESP à long terme.
